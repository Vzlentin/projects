# projects reference

`@vzlentin/projects` is the projects entry of a harness host. A host is the harness unit: one host process, with its name, its directory, its host agent and its state directory. A project is what the projects entry makes of a host: the persons, the threads, the rules, the parleys and the work items of the host, the section of the decided rules and the digest before each input.

This file gives the behaviour of the entry. The behaviour of the host, such as the entry API, the asks, the push and the life of the agents, is in the [harness spec](https://github.com/Vzlentin/harness/blob/f1cdbeb1496985c40c5fc24b598ffc865458f00c/docs/spec.md) at the commit that this package pins. The links to `harness spec` below go to it.

## Entry

The projects entry is the module `src/projects/index.ts` (`dist/projects/index.js` in a build). The package exports it as `@vzlentin/projects/entry`. It also exports, for the Pi package, `@vzlentin/projects/project-tool` (`src/project-tool.ts`), `@vzlentin/projects/memory-tool` (`src/memory-tool.ts`) and `@vzlentin/projects/protocol/<name>` (`src/protocol/<name>.ts`), and no other module. A host loads the entry only as an external entry, as any entry of the [harness spec, Host](https://github.com/Vzlentin/harness/blob/f1cdbeb1496985c40c5fc24b598ffc865458f00c/docs/spec.md#host): from `$XDG_CONFIG_HOME/harness/entries.json`, where `setEntry(name, module)` of `@vzlentin/harness/entries` names the module of the entry, or from `piDurable.extensions` of the `package.json` of an installed Pi package. The Pi package `@vzlentin/pi-projects` (`pi/`) names `./entry.js` in `piDurable.extensions`: one line that exports the default export of `@vzlentin/projects/entry` (see [Pi package](#pi-package)). Name the entry at one of these two places, not at both. When `entries.json` names the projects entry and a host also loads it from pi-projects, the two modules are two entries with the same request types, input hook and protocol, and the host refuses to start with `The entries <module> and <module> both <what>`, such as `both give the input hook digest`. A host that runs already loads the entry only after it starts again.

A host without the projects entry runs, with no rules section, no digest, no memory of the host agent and no project tools. It answers a request of a type of this entry, such as `parley` or `item`, with `no loaded entry serves request type "<type>"` (see the [harness spec, Host](https://github.com/Vzlentin/harness/blob/f1cdbeb1496985c40c5fc24b598ffc865458f00c/docs/spec.md#host)).

The host calls the default export of the entry with the handles of the entry API (`EntryOptions` of `@vzlentin/harness/entry-api`). The entry reaches the state of the host only through these handles. It uses `options.host`, the name of the host, for the digest and for the memory folder, `options.cwd`, the directory of the host, for the memory folder, `options.stateDir`, the state directory of the host, for `project.sqlite`, and `options.settings` and `options.place.models` for the model of the compressions (see [Memory](#memory)). The entry returns:

- `extensions`: three pi-durable extensions, in this order. `harness-rules` gives the section of the decided rules (see [Rules section](#rules-section)). `harness-memory` (`MEMORY_EXTENSION`) gives the `memory` tool and the memory section (see [Memory](#memory)). `harness-project` gives the tools `thread`, `rule`, `parley` and `item` (see [Tools](#tools)).
- `uninherited`: `["harness-memory"]`, so only the host agent has the memory. At any depth, `children.open` removes this extension from the `extensions` of the `AgentDoc` of each child (see `uninherited` in the [harness spec, Host](https://github.com/Vzlentin/harness/blob/f1cdbeb1496985c40c5fc24b598ffc865458f00c/docs/spec.md#host)).
- `requests`: the request types `person`, `thread`, `message`, `digest`, `memory`, `rule`, `parley`, `item` and the watch `watch-project` (see [Requests](#requests)).
- `input`: the input hook of the kind `digest` (see [Digest](#digest)).
- `answeredAsk`: the handler of the answered asks, which makes the contracts of the parleys (see [Contracts](#contracts)).
- `reported`: the handler of the reports, with the rule of the items (see [Reports](#reports)).
- `labels`: the checks of the label kinds `parley` and `item` (see [Labels](#labels)).
- `protocol`: `{ name: "projects", version: 1 }`. The `hello` reply of the host gives it in `entries`, as `{ "projects": 1 }`. `PROJECTS_PROTOCOL_VERSION` of `src/projects/index.ts` is the version.
- `ask`: the handler of the `ask` requests, with their parleys (see [Parleys](#parleys)).
- `open`: the open steps below.
- `busy`: true while a compression of the memory runs, so the host does not take its idle exit (see [Memory](#memory)).
- `close`: stops the compressions of the memory and waits until they end, then closes `project.sqlite`.

The entry gives no `catchUp` and no `tasks`.

### Open

The host calls `open({ harness, root, storage })` of the entry once the store, the root conversation and the workers are there. The entry runs these steps, in order:

1. It opens `project.sqlite` in the state directory of the host. When `project.sqlite` is not there, it creates an empty one. It never reads `store.json` and never writes it: `projects store load` writes a store file into `project.sqlite` (see [store load](#store-load)).
2. It moves the open todos of the list of the host agent to work items, once (see [Move of the todos](#move-of-the-todos)).
3. It gives the children of the `serves` edges of an old store their labels, once (see [Move of the labels](#move-of-the-labels)).
4. It stops each live worker of a parley or an item that is done or dropped, such as a child that a message resumed after the end of its work (see [Workers of the work](#workers-of-the-work)).

A failure of steps 1 to 3 stops the start of the host, and a failure of step 2 or 3 also closes `project.sqlite`. Step 4 writes a warning for a failure, and the start goes on. Until the open ends, each handler of the entry that needs the store throws `The host is not open yet`.

### Degraded states

The entry starts and ends the degraded state `digest-failed` through the `degraded` handle (see the degraded states in the [harness spec, Host](https://github.com/Vzlentin/harness/blob/f1cdbeb1496985c40c5fc24b598ffc865458f00c/docs/spec.md#host)), with the conversation ID as its cause: the digest of the conversation failed. The line is `digest: <message>`. It ends at the next digest of the conversation that works or has nothing to write.

## Requests

The entry serves these request types on the socket of the host. The host checks each line against the schema of its type, the branches of `ProjectRequestLine` of `src/protocol/requests.ts` for that type, and a line that does not match fails with `Invalid <type> request: <path>: <rule>`. A typed request of `scope.send` gets the same check. `Replies` of the same module gives the value of the reply to each type.

| Type            | Actions                                                       | Passive for the idle exit |
| --------------- | ------------------------------------------------------------- | ------------------------- |
| `person`        | `add`, `list`                                                 | `list`                    |
| `thread`        | `add`, `list`, `read`, `join`                                 | `list`, `read`            |
| `message`       | `log`, `mark`, `edit`, `delete`                               | none                      |
| `digest`        | none                                                          | no                        |
| `memory`        | `note`, `recall`, `zoom`, `snapshot`                          | none                      |
| `rule`          | `set`, `list`, `decide`, `retire`, `edit`, `create`, `delete` | `list`                    |
| `parley`        | `take`, `end`, `read`, `list`                                 | `list`, `read`            |
| `item`          | `add`, `set`, `list`, `read`, `link`, `unlink`                | `list`, `read`            |
| `watch-project` | none                                                          | yes                       |

A passive request does not count as activity for the idle exit of the host. An open `watch-project` is a connection, so it keeps the host running. The `ask` requests are types of the host: the host decides their passive rule, and the entry serves them through its `ask` handler (see [Parleys](#parleys)).

A request that fails changes nothing. Every time is in epoch milliseconds. Each reply of a list is in ID order.

## Project store

The entry keeps the persons, the threads with their persons, the messages, the rules, the parleys and the work items of the host in `project.sqlite`, in the state directory of the host, as plain tables: `person`, `thread`, `thread_person` for the persons of each thread in the order that they joined, `message`, `rule`, `parley`, `item`, and `edge`, the edges of the items, with an index on `from` and one on `to`. An author that is `user` is NULL in its person column. The evidence of a parley is a JSON array of texts. The asks stay in `durable.sqlite`, in the document of the session `harness.asks`, and the host is their one writer (see the [harness spec, Asks and parleys](https://github.com/Vzlentin/harness/blob/f1cdbeb1496985c40c5fc24b598ffc865458f00c/docs/spec.md#asks-and-parleys)).

The entry is the only writer of `project.sqlite`: each request writes in one transaction, and a request that fails rolls it back. A write of a parley and of asks writes `project.sqlite` in the commit of `durable.sqlite`, and `watch-project` reads the two stores only once the commit is done. A person, a thread, a message, a rule, a parley and an item have the next ID of their list, 1, 2, 3 and so on, and no ID is given twice in a list, also after a delete: the ID of a deleted message or rule is never given again, and the other objects keep their IDs. A thread is not a node of the tree. An author, `from` or `saidBy`, is the ID of a person or `"user"`.

### Store file

A store file is a JSON file of version 3 that holds the lists of the store of a project. `projects store load` writes it into `project.sqlite` (see [store load](#store-load)). `store load` refuses a file of another version.

`store load` checks the file before it opens a store. A file with a `version` other than 3 fails with `<file> has the version <version>: projects store load reads only the version 3`. A file that is not JSON, that does not match the schema of a store file, that has an ID twice, or whose references do not resolve fails with `<file> is not a store file: <reason>`:

- Each ID is there once in `persons`, `threads`, `rules`, `parleys`, `asks`, `todos`, `items` and each list of `callerTodos`. Each message ID is there once in all the threads together, and each caller is there once in `callerTodos`.
- Each message names its thread. The `source` of each rule names a message of the file. The `ask` of each todo of `todos` and of `callerTodos` names an ask of the file, else it fails with `the ask of the todo <id> is no ask of the file`, or `the ask of the todo <id> of <caller> is no ask of the file` for a list of `callerTodos`.
- Each edge of an item is an edge of that item: its kind takes its ends, and the item that stores it is the item, the `from` item for an edge from an item, else it fails with `the edge <from> <kind> <to> is not an edge of the item <id>`.
- Each `needs` edge goes to an item of the file, else it fails with `the edge <from> needs <to> goes to no item of the file`. The `needs` edges of the file make no cycle, an edge from an item to itself included, else it fails with `the needs edges make a cycle through the item <id>`, where `<id>` is an item of the cycle.

The file is a JSON object with `version` (3) and one key for each list: `persons`; `threads`, each thread with its `messages`, oldest first, each with its state, and each message out with `changed`, `{ at, by }`, the last change of its state; `rules`; `lastRule`, the highest ID that a rule had, 0 when no rule was set; `parleys`; `asks`; `todos`, the list of the host agent, each todo with its `ask` when it has one; `callerTodos`, `[{ caller, todos }]` for each caller that is not a conversation of the host, such as a Pi session, in caller order; `items`, every item in ID order, each with its edges; and `lastItem`, the `last` of the counter of the IDs of items, 0 when the store has no counter. The schema gives each message out `changed` and no message in. `StoreFile` of `src/protocol/store-file.ts` is its schema, and `STORE_FILE_VERSION` its version.

### Move of the todos

When `project.sqlite` has no counter of the IDs of items, the open moves the open todos of the list of the host agent to items, once. Each todo that is `open` or `doing` and has no `ask` becomes the open item with the same ID, its text as the `title`, no `text`, and `by` `migration`, and stays in the list as `dropped`, with the text `moved to item <id>: <text>`. `last` of the counter is the highest ID of the list, moved or not, so a new item never takes the ID of an old todo. An ID up to `last` that has no item, such as the ID of a todo that was done, is an unknown item. The move writes the list in one commit of `durable.sqlite`, and the items and the counter in one write of `project.sqlite` in that commit.

### Move of the labels

At its first open, the entry gives the child of each edge `agent:<conversation ID> serves item:<id>` the label `item:<id>` with `labelChild`. Then it takes these edges from their items in one write of `project.sqlite`, in the commit that writes the document `harness.label-move`. An edge whose conversation is no child of the host stays. An open that finds `harness.label-move` reads no item and writes nothing. An open after a failure before that commit moves the edges again, and adds each label once. A child of an item that no edge names gets no label.

## Persons, threads and messages

Each write, `message log`, `message mark`, `message edit`, `message delete`, each `rule` request but `list`, and each `item` request but `list` and `read`, has a `caller`, as a `todo` request of the host has: the conversation ID of a hosted agent, a Pi session ID, or another text. The entry keeps it in `by` of the object that the write adds or changes. `person add`, `thread add` and `thread join` have no `caller`.

- `person add { name }` adds a person `{ id, name }`, and replies with it. `person list` replies with `{ persons }`.
- `thread add { topic, persons }` adds a thread `{ id, topic, persons, last? }` with one or more persons, and replies with it. `last` is the latest `at` of its messages, absent while it has none. `thread list` replies with `{ threads }`. `thread read { id }` replies with `{ thread, messages }`, the messages oldest first, in ID order. `thread join { id, person }` adds the person `person` to the thread `id`, and replies with the thread. A person of the thread fails with `Person <person> is already in thread <id>`.
- `message log { caller, thread, from, direction, at?, text, state? }` adds a message `{ id, thread, from, direction, state, at, text, by }` to the thread, and replies with it. `direction` is `in` or `out`. The entry sets `state`: `received` for `in`, `draft` for `out`. With `state: "sent"`, a message `out` gets the state `sent` and is never a draft. `sent` is the only value of `state`: another value fails with `Invalid message request: state: <rule>`, and `sent` for a message `in` with `Only a message out can be logged as sent`. `at` defaults to the time of the write. A message `in` from a person of the thread is a reply to each message out of the thread in the state `draft` or `sent` whose `at` is not later than its own: in the same write, a draft becomes `sent`, and a sent message `answered`. One message moves each of them one step only. A pasted message that is older than the draft moves nothing.
- `message mark { caller, message, state }` sets the state of the message out `message`, and replies with it. `state` is `sent` (the user sent it, such as after a copy), `draft` (it was not sent after all) or `dropped`. A draft takes `sent` and `dropped`, and a sent message takes `draft`. Another mark fails with `Message <id> is <state>: it cannot become <state>`, and a mark of a message in with `Message <id> is a message in: only a message out has a mark`. The states of a message out are `draft`, `sent`, `answered` and `dropped`. `messageTransition(state, event)` of `src/protocol/project.ts` gives the state after a mark or a reply, or `undefined`.
- `message edit { caller, message, text, at?, from? }` changes the message `message`, and replies with it. It gets `text`, and `at` and `from` when they are given: else it keeps its own. Its ID stays the same, and `by` becomes the caller. `direction` is `out` for `user` and `in` for a person. A `from` that is a person must be a person of the thread: another person fails with `Person <from> is not in thread <thread>`. A message out that stays a message out keeps its state and the last change of its state, and the reply rule compares its new `at`. A message in stays `received`. A message out that becomes a message in is `received`. A message in that becomes a message out is a `draft`, as for `message log`. The edit moves no other message. `last` of the thread becomes the latest `at` of its messages, so an earlier `at` can lower it.
- `message delete { caller, message }` removes the message `message`, and replies with it as it was, with its state. A rule that is not retired and has the message as its `source` fails the delete with `Message <message> is the source of rule <id>`. A retired rule with the message as its `source` loses its `source` and its `thread` in the same write, and keeps its `at` and `by`. The `data.waits` of an old `harness.digest` entry can also name a message, and does not block a delete: no read gives it back. `last` of the thread becomes the latest `at` of the messages that remain, and goes when none remains. A deleted message is an unknown message for every request.

No tool sends `thread add`, `thread join`, `message edit` or `message delete`.

An unknown ID fails with `Unknown person: <id>`, `Unknown thread: <id>` or `Unknown message: <id>`, for the persons of a thread, an author and a message. `thread join` checks its person first. An empty `name`, `topic` or `text`, or a thread with no person, fails with `Invalid <type> request: <field>: <rule>`.

## Rules

A rule is `{ id, name, kind, value, status, saidBy, source?, thread?, words?, replaces?, at, by }`. `kind` is `conduct` (how an agent acts) or `domain` (a fact of the project). `status` is `open`, `decided` or `retired`. `source` is the ID of a message. `thread` is the ID of the thread of the message `source`: the entry sets it with `source`, so a changed source gives the thread of the new source, and a rule with no source has no `thread`. `words` is the exact words of the user that say the rule, as an agent recorded them. `at` is the time of the last change, and `by` the caller of that change.

- `rule set { caller, saidBy, source, ... }` is the request of an agent. Without `id`, it adds a rule with `name`, `kind` and `value`, in the status `open`. `replaces` names the rule that the new rule replaces, which must exist; it changes nothing until the user decides the new rule. With `id`, it changes the open rule `id`: its `name`, `kind` and `value` when they are given, and always its `saidBy`, `source`, `thread`, `at` and `by`. `rule set` has no `status`. The reply is the rule.
- `rule set { caller, saidBy: "user", words, ... }` is the same request with the exact words of the user in place of `source`: the user stated the rule to the agent. The entry checks nothing more. The rule gets `words` and no `source` and no `thread`, and becomes `decided` in the same write, as a `decide` makes it: the rule that it replaces becomes `retired`. With `id`, the open rule `id` gets the words, loses its `source` and its `thread`, and becomes `decided`.
- `rule list { kind?, status? }` replies with `{ rules }`, only those of the kind `kind` and of the status `status` when they are given.
- `rule decide { caller, id }`, `rule retire { caller, id }`, `rule edit { caller, id, name?, kind?, value? }`, `rule create { caller, name, kind, value }` and `rule delete { caller, id }` are the changes that only the user makes. `decide` makes an open rule `decided`, and makes the rule that it replaces `retired` when that rule is still there and not retired, with the `at` and the `by` of the write; the retired rule keeps its own `saidBy`, `source` and `thread`. `retire` makes an open or a decided rule `retired`. `edit` changes the `name`, `kind` and `value` that it gives of a rule in any status, and keeps the status; the rule gets `saidBy` `user` and no `source`, no `thread` and no `words`. `create` adds a rule in the status `decided`, with `saidBy` `user` and no `source` and no `thread`. `delete` removes the rule. The reply is the rule, for `delete` the rule as it was.

No tool of an agent sends the changes of the user. The entry cannot tell who sends a request: a Pi session and its agent share one caller, the session ID, and any process can write to the socket of the host. The barrier is that no tool sends these requests. A `bash` call of an agent that runs `projects rule decide` and a raw write to the socket of the host are not stopped.

A write without `caller`, and a `set` without `saidBy`, or with neither `source` nor `words`, fails with `Invalid rule request: <field>: required`; the field is `source` for a `set` with neither. A `set` with both `source` and `words` fails with `Invalid rule request: words: not allowed`, and a `set` with `words` and a `saidBy` that is not `user` with `Invalid rule request: source: required`. A `set` with `id` and `replaces` fails with `A change of a rule cannot replace a rule: set replaces on a new rule`. A `set` with `status` fails with `Invalid rule request: status: not allowed`. A `set` with `id` or a `decide` of a rule that is not open fails with `Rule <id> is <status>, not open`, and a `retire` of a retired rule with `Rule <id> is retired`. An unknown ID fails with `Unknown message: <id>` for a source, `Unknown person: <id>` for an author, and `Unknown rule: <id>` for a rule that a new rule replaces and the rule of a change. An empty `name`, `value` or `words` fails with `Invalid rule request: <field>: <rule>`.

A `project.sqlite` whose table `rule` has no column `words` gets it when the entry opens the store, and its rules keep their fields.

### Rules section

A conversation of the host has the section `project_rules` (`RULES_SECTION` of `src/protocol/project.ts`) in its system prompt when the project has decided rules. The extension `harness-rules` of the entry gives it. It reads the decided rules of `project.sqlite` at each model request, so a rule that the user decides or retires reaches a running agent at its next request, with no restart. `rulesSection` of `src/protocol/project.ts` gives the text: the line ``A rule is what a person of the project said that each agent follows (conduct) or knows as true (domain); only the user puts a rule in effect. Propose a rule with the `rule` tool, and never write a rule into `AGENTS.md`.``, then the decided conduct rules and the decided domain rules, each group in ID order, each rule as `<id> <name> (<kind>): <value>`. With no decided rule, the section is absent.

## Parleys

A parley is a group of asks with a frame, which ends as a contract. The entry keeps the parleys in the table `parley` of `project.sqlite`, and serves the `ask` requests of the host in place of the plain asks, with its `ask` handler. The host keeps the asks, and the [harness spec, Asks and parleys](https://github.com/Vzlentin/harness/blob/f1cdbeb1496985c40c5fc24b598ffc865458f00c/docs/spec.md#asks-and-parleys) gives the ask, its fields, its states, its author, the queue of the answers for their askers and the todo `Save to the vault`. An ask names its asker, and its parley when it has one. A parley names no asker and no ask.

A parley is `{ id, slug, title, goal, evidence?, design_sense?, status, at, by }`. `slug` is lowercase words of letters and digits joined by hyphens, unique in the host. `evidence` is a list of texts that is not empty. `status` is `open`, then `contract`, then `done` or `dropped`. A parley that is not open has `design_sense`. `at` is the time of its last change, and `by` the caller of that change. `title`, `goal`, `design_sense` and each text of `evidence` are plain text: at least one character that is not white space, with no backtick and no `**`.

The `parley` of an ask is `{ id, n }`: the ID of its parley, and its number in that parley, 1, 2, 3 and so on. The number never changes. The read-back of a parley is an ask of the parley with no options: its answer is `ok` or `own`.

A request names one ask as `{ id }`, its ID, or as `{ slug, n }`, its number `n` in the parley `slug`. The reply of a write of asks, `{ parleys, asks }`, comes from the commit of the write: `parleys` has each parley that the write changed, or whose asks it changed, as `{ parley, asks }` with all of its asks, in the order of their numbers, and `asks` has the asks with no parley that the write added or changed, in ID order. The entry gives no `items` in a reply: no write of asks adds an item.

- `ask round { caller, parley?, item?, asks }` writes one or more asks, with the state `open` and the caller as their asker. With `parley`, `asks` can be empty: the round then only changes the frame of the parley. With `parley` `{ slug, title?, goal?, evidence?, design_sense? }`, the asks serve the parley `slug`, and take its next numbers. A new slug makes an open parley, which needs `title` and `goal`. A known slug must be an open parley, and the fields that `parley` gives replace its own. An entry of `asks` with `ask`, the number of an open ask of the parley, replaces the question of that ask: its `title`, `kind`, `tension`, `options`, `plan` and `view`, and a field that the entry does not give is removed. The ask keeps its ID, its number, its asker, its state and its note, and gets the `at` and the `by` of the round. The store keeps no old version of the question. The other entries are new asks, which take the next numbers. The entry checks each `ask` before the round writes anything, and replaces the question with the `replace` handle of the host asks, before it writes the parley. A round with no asks needs a known open parley, and one of `title`, `goal`, `evidence` and `design_sense` that differs from the value of the parley; else it fails with `A round with no asks must change the title, goal, evidence or design sense of the open parley <slug>`, also with a new slug. With `item`, the ID of an item, which needs `parley`, the round also writes the edge `parley:<slug> shapes item:<item>` with the checks and the errors of `item link`, after it writes the parley: an equal edge is not written again. A round with `item` and no `parley` fails with `Invalid ask request: parley: required`. The parley and its edge go to `project.sqlite` in one write in the commit of the asks. The reply is the write: the parley with its asks, or the new asks when they have no parley.
- `ask answer { caller, answers, user? }` writes one or more answers `{ id, answer, label?, words? }` or `{ slug, n, answer, label?, words? }` in one write, each of another ask. An answer to an ask of a parley needs an open parley. An answer `ok` to a read-back needs a parley that can be a contract after every answer of the write: each other ask of the parley is answered or dropped, and its `design_sense` is set. The parley stays `open` in the write: the event of the answered read-back makes it `contract` a moment later (see [Contracts](#contracts)). The host sets the `author` of each answer, and the read-backs get no todo `Save to the vault`. The answers go to their askers in one delivery for each asker and parley, with the text of the parley after the write, where a parley whose read-back got `ok` is still `open`, as the `read` of the `parley` tool gives it, and one delivery for each answered ask with no parley. The reply is the write: each parley of the answered asks, with its status after the write, and the answered asks with no parley.
- `ask drop { caller, id }` or `ask drop { caller, slug, n }` drops an open ask of an open parley, or an open ask with no parley, and replies with the write: its parley, or the ask when it has no parley.
- `ask note { caller, id, note }` or `ask note { caller, slug, n, note }` sets `note`, the ID of the vault note of the ask, as the host does, and replies with the ask. The ask can be in any state, and its parley in any status.
- `ask read { id }` or `ask read { slug, n }` replies with the ask, in any state.
- `ask list` replies with `{ asks }`, the open asks.
- `parley take { caller, slug }` makes the caller the asker of each open ask of the parley `slug`, which is open or a contract, and replies with `{ parley, asks }`. A contract has no open ask, so its take changes no ask. The answers of the parley that wait for an asker leave the queue in the same write: the taker has them in the reply, and no asker gets them after.
- `parley end { caller, slug, status }` ends the parley `slug`, and replies with the parley. A contract ends with the status `done` or `dropped`. A contract that shapes an open item does not end: the change of its last open item to `done` or `dropped` ends it (see [Work items](#work-items)). So `parley end` ends only a contract that shapes no item, or whose items are all closed. An open parley ends only with the status `dropped`: each of its open asks is dropped, and its answered and dropped asks stay as they are. It keeps its `design_sense`, or gets `None: the parley was dropped while open.` when it has none. An edge `shapes` of the parley stays, and the parley no longer gives its item the stage `shaping` (see [Stages](#stages)). The asks and the parley change in one commit of the asks, and the parley goes to `project.sqlite` last. After the write, it stops the live workers of the label `parley:<slug>` (see [Workers of the work](#workers-of-the-work)).
- `parley read { slug }` replies with `{ parley, asks }`, the asks in the order of their numbers. `parley list` replies with `{ parleys }`.

No request removes a parley. A slug that is not valid, and a text that is not plain, fail with `Invalid ask request: <path>: <rule>` or `Invalid parley request: <path>: <rule>`. The checks of the plain asks of the host also apply (see the [harness spec, Asks and parleys](https://github.com/Vzlentin/harness/blob/f1cdbeb1496985c40c5fc24b598ffc865458f00c/docs/spec.md#asks-and-parleys)), such as `Ask <id> takes <keys> or own`, which is `Ask <id> takes ok or own` for a read-back. The checks against the store fail with:

- `Unknown parley: <slug>`, and `Parley <slug> has no ask <n>`.
- For a round with an entry with `ask`: `A round that replaces an ask needs a parley`, without `parley`; `Invalid round: ask must be the number of an ask of the parley`, for an `ask` that is not an integer of 1 or more; `Unknown parley: <slug>`, for a new slug; `<slug> ask <n> is <state>: only an open ask is replaced`; and `Round replaces <slug> ask <n> twice`. The round then writes no frame, no edge and no ask.
- `Ask <id> has two answers in one write`, also when an answer by ID and an answer by number name the same ask.
- `Parley <slug> is new: title is required`, and the same for `goal`.
- `Parley <slug> is <status>: its asks do not change`, for a round, an answer or a drop on a parley that is not open, and for a take on a parley that is done or dropped.
- `Parley <slug> cannot be a contract: ask <n> is open`, and `Parley <slug> cannot be a contract: design_sense is not set`, for an answer `ok` to a read-back while another ask of the parley is open after the write, or without a design sense. The write then changes nothing.
- `Parley <slug> is open: it ends only as dropped`, for a `parley end` of an open parley with the status `done`.
- `Parley <slug> is <status>: only an open parley or a contract ends`, for a `parley end` of a parley that is done or dropped.
- `Parley <slug> shapes open items <ids>: close them, and the contract ends`, for a `parley end` of a contract that shapes open items, with their IDs in ID order, joined with `, `.
- For a round with `item`: `Unknown item: <id>`, and `Item <id> is <state>: an edge shapes cannot go to it`.

### Contracts

The `answeredAsk` handler of the entry gets each answered ask (see the entries in the [harness spec, Host](https://github.com/Vzlentin/harness/blob/f1cdbeb1496985c40c5fc24b598ffc865458f00c/docs/spec.md#host)). For the read-back of a parley, it makes the parley `contract` in its own write of `project.sqlite`, in a commit of the asks, with the `by` of the answered read-back as its `by`. That write reads the store as it is then. A parley that is not open at that time, and a read-back that is not answered `ok` at that time, change nothing, so a second event of the same answer does nothing. A parley that cannot be a contract then, such as one where a later round added an open ask, gives the warning `Parley <slug> cannot be a contract: ...` and stays open. A contract that no item has an edge `shapes` from gets, in the same write, a new open item with the title of the parley, no text, and the `by` of the read-back as its `by`, and the edge `parley:<slug> shapes item:<id>`. A contract that shapes an item gets no new item. An open parley does not stop its workers when it becomes a contract.

## Work items

A work item is a piece of work, `{ id, title, text?, state, edges, at, by }`: `title` is one line, `text` says in Markdown what to build, `state` is `open` (work to do), `done` (the work ended as intended) or `dropped` (given up), `edges` are its links in the order of their writes, `at` is the time of its last change and `by` the caller of that change.

A reference is a text `<kind>:<value>`, where the value is the ID that the kind already has: `item:<id>`, `agent:<id>` with the ID of a conversation that the children library opened, `run:<id>` with a workflows run ID (`<8 digits>T<6 digits>-<8 hex digits>`), `parley:<slug>`, and `commit:<sha>` with a full SHA (40 lowercase hex digits). An edge `{ from, kind, to, at, by }` is a link between two references, one of them an item, and never changes after its write. Its kind fixes its ends: `serves` goes from an agent or a run to an item, `shapes` from a parley to an item, `landed` from an item to a commit, and `needs` from an item to another item, which the first item waits for. Each item is one row of the table `item`, and each edge one row of the table `edge`, which keeps the order of the writes. An edge from an item, `landed` or `needs`, is an edge of its `from` item, and another edge of its `to` item. The counter of the IDs of items, `last`, is the row `item` of `sqlite_sequence`. `item add` gives the ID after `last` and raises `last` in the same write, so an ID is never given twice. `item add` and the write that makes a parley a contract add items. The move of the todos and `store load` write the counter.

Each `item` request has an `action`:

- `item add { caller, title, text? }` adds an open item with no edge, and replies with it.
- `item set { caller, id, title?, text?, state? }` changes the fields that it gives, and replies with the item. A `text` of `""` stores an empty text: no request removes `text`. A `state` of `done` fails with `Item <id> cannot be done: run <runId> serves it and is live` while a run of the started tasks with the label `item:<id>`, whose keys are `wf:<runId>#<n>`, in any state of the task, is live (see [Stages](#stages)), also for an item that is already done. The entry reads its `serves` edges for no refusal. A live started task with the label whose key is of another form refuses it with `Item <id> cannot be done: task <key> serves it and is live`. A live agent with the label does not refuse it, so an agent can set its own item to `done`. When the write gives a state of `done` or `dropped`, it ends, in the same write, each contract that shapes the item and no open item, with the caller as its `by`: with the status `done` when one item that it shapes is `done`, else `dropped`. This also holds for an item that is already closed, so a contract whose items were all closed before ends at the next such change. An item that goes back to `open` does not reopen its contract. After the write, when the item is not open, the entry stops the live workers of the label `item:<id>`, and of the label `parley:<slug>` of each contract that the write ended (see [Workers of the work](#workers-of-the-work)).
- `item list { state? }` replies with `{ items }`: the items in the state `state`, default `open`, in ID order.
- `item read { id }` replies with the item, in any state, with its edges, then the `needs` edges of the other items that go to it, in the ID order of those items. The other replies, `watch-project` and a store file give only the edges that the item stores.
- `item link { caller, from, kind, to }` checks the edge, writes it as the last edge of its item, and replies with it. The entry checks, in this order: the kind takes the ends, else `An edge <kind> cannot go from <from> to <to>`; a `needs` edge does not go from an item to itself, else `An edge needs cannot go from <from> to itself`; the item exists; when the item has an edge with the same `from`, `kind` and `to`, the reply is that stored edge, with its own `at` and `by`, and nothing is written, so a resumed run can send its link again; a new `serves` edge to an open item from an agent fails with `An agent serves an item through its label: spawn it with serves`, and from a run that already serves an item with `Run <runId> already serves item <id>`, so a run serves one item at most; a `serves` or `shapes` edge needs an open item, else `Item <id> is <state>: an edge <kind> cannot go to it`, and a `needs` edge an open `from` item, else `Item <id> is <state>: an edge needs cannot go from it`; a parley end is a parley of the store, else `Unknown parley: <slug>`; the `to` item of a `needs` edge exists, in any state, else `Unknown item: <id>`; a `needs` edge makes no cycle: when the `to` item needs the `from` item, through its `needs` edges and those of the items that it needs, the link fails with `Item <to> already needs item <from>: an edge needs cannot make a cycle`. A run end and a commit end are checked for their form only: the entry keeps no runs by ID and no commits. A `landed` edge goes from an item in any state.
- `item unlink { caller, from, kind, to }` removes an edge that was written by mistake, and replies with the item. It checks the ends and the item as `link` does. An edge that the item does not have fails with `Item <id> has no edge <from> <kind> <to>`. No tool sends it.

A link and an unlink do not change the `at` and the `by` of the item. An ID that no `item add` gave fails with `Unknown item: <id>`. A reference, a kind or a state of another form, an empty `title`, and an `id` below 1 fail with `Invalid item request: <field>: <rule>`. The indexes of the table `edge` on `from` and on `to` give the items of each `agent:`, `run:` and `parley:` end, such as the items that a parley shapes, and the `needs` edges that go to an item.

`WorkItem`, `StagedItem`, `Edge`, `Ref`, `ItemCounter` and `ItemList` of `src/protocol/item.ts` are the TypeBox schemas of an item as the store keeps it, an item with its `stage` and `needsYou` as a reply gives it, an edge, a reference, the counter and the reply of `item list`. `ItemAdd`, `ItemSet` and `EdgeInput` are the schemas of the inputs, `ItemStage` the schema of a stage, and `EDGE_KINDS`, `ITEM_STATES` and `ITEM_STAGES` the kinds of an edge, the states of an item and its stages.

### Stages

Each reply that gives an item, the replies of `add`, `set`, `read` and `unlink` and each item of `list`, gives it with `stage` and `needsYou`, which the entry works out at each reply from the item and the other ends of its edges, and never stores. `stage` is the column of the item on a board: the first of these checks that holds gives it.

1. The state `done` or `dropped` gives that state.
2. A live worker of the label `item:<id>` (see [Workers of the work](#workers-of-the-work)), or a run that serves the item and is live, gives `building`.
3. A parley with the status `open` that shapes the item gives `shaping`.
4. A parley with the status `contract` that shapes the item gives `ready`.
5. Else the stage is `inbox`.

A run serves the item through a `serves` edge, or through a started task with the label `item:<id>` whose key is `wf:<runId>#<n>`, in any state of the task. A run is live while a live worker of the label `item:<id>` is a task that `start` created with the key `wf:<runId>#<n>`, where `n` is an integer from 1 (a task that is not terminal), and while an ask with the asker `workflows:<runId>` is open: the task of a run that waits for an input of the user is terminal, and its open ask keeps the run live.

`needsYou` is true when one of these holds: an ask of a parley that shapes the item is open; an open ask has as its asker the conversation of a live agent with the label of the item, or `workflows:<runId>` of a run that serves it. `needsYou` reads the same inputs for an item in any state.

### Reports

The `reported` handler of the entry gets each `report` of a worker (see the task requests in the [harness spec, Host](https://github.com/Vzlentin/harness/blob/f1cdbeb1496985c40c5fc24b598ffc865458f00c/docs/spec.md#host)). A `report` of a worker with the label `item:<id>` closes the item as a landed commit: in one write of `project.sqlite`, for each reference `commit:<40 hex>` of the report, it writes the edge `item:<id> landed commit:<sha>` with the caller of the report as its `by`, as `item link` does, so a repeat writes nothing, and it sets an open item `done` and ends its contracts as `item set` does, with no refusal for a live run or task. A closed item keeps its state, so a dropped item stays dropped and gets the edge. After the write, it stops the live workers of each item that it set `done` and of each contract that it ended, but the reporter. The reporter may still land its work, and the next open of the entry stops it when it is still live. A label whose value is not an item ID, or that names no item of the store, and the other references change no item. A report with no commit reference changes no item.

## Workers of the work

A worker is a child of the host or a started task with a label (see the [harness spec, Agent life](https://github.com/Vzlentin/harness/blob/f1cdbeb1496985c40c5fc24b598ffc865458f00c/docs/spec.md#agent-life)). The entry stops the workers of the work of the project when that work ends, with their subtree, through the `stop` and `stopAfterTurn` handles:

| Label           | Stops when                                                                                 |
| --------------- | ------------------------------------------------------------------------------------------ |
| `parley:<slug>` | the parley is done or dropped: `parley end`, or the end of its last item                   |
| `item:<id>`     | `item set` leaves the item done or dropped, or a `report` of a commit sets the item `done` |

The stop comes after the commit of the change, before its reply, whatever the todos of the worker; a busy turn is aborted, which gives `<handle> was aborted`. The agent worker whose conversation is the caller of the change, such as a child that sets its own item `done` with `item set` or ends its parley with `parley end`, is not aborted: it stops after its turn, at the commit that ends the turn, or at once when it runs no turn. The reply does not wait for that stop, so the other tool calls of its turn run to their end. A worker that is already ended stays as it is. A `report` that sets an item `done` does not stop the reporter. A failed stop is a warning in `host.log`. A message resumes a stopped child; at each open, the entry stops each live worker of an item or a parley that is done or dropped, such as a child that a message resumed. A worker of a parley or an item that the store does not have stays as it is.

### Labels

The entry checks the label kinds `parley` and `item`. The host calls the check before a spawn or a first start with a label of the kind, and before the commit that creates the worker, so a parley or an item that ends between the check and the commit leaves its worker until the next open. The check refuses:

- an unknown parley with `Unknown parley: <slug>`, and a parley that is done or dropped with `Parley <slug> is <status>: an agent cannot serve it`. An open parley and a contract pass.
- an unknown item, or an item value that is not an integer from 1, with `Unknown item: <value>`, and an item that is done or dropped with `Item <id> is <state>: an agent cannot serve it`.

A spawn writes no edge into an item: an agent serves an item through its label.

## Digest

A `digest` request `{ caller, head? }` replies with `{ text }`, the digest of `caller`, and records it in the document `harness.digests` as the last digest of the caller. The digest has these lines:

1. `board of <host>: <n> open`, where `<host>` is the name of the host and n counts the open items, also when it is 0.
2. Up to 10 lines `○ <id> <title>`, the open items in ID order that have no open need. An open need is a `needs` edge of the item to an item in the state `open`; an edge to a closed or an unknown item is none.
3. `+<n> later` when the board does not show n > 0 open items, those with an open need and those after the first 10.
4. `waiting on: ` and each message out in the state `draft` or `sent`, as `<persons> (<topic>, sent <day> <month> <HH:MM>)` or `<persons> (<topic>, draft not sent)`, with the names of the persons of its thread and the time of its last change of state in UTC, such as `Sam (own-brand C+P, sent 12 Nov 14:22)`.

The items of a line are joined with `·`, and an empty list is `none`. `head` is the ID of the newest head of the context of the caller. The record keeps the `head` of every caller, and a new `head` gives the digest again, also when the text is the same, with the next count. The reply is `{}` when the text and the `head` are those of the last digest of the caller, and when the caller never got a digest, no message waits and no item is open.

The input hook of the kind `digest` gives each hosted conversation its digest the same way, as a passive user entry of the kind `harness.digest` with `data` `{ waits, items }`, the IDs of the messages and of the items on the board. The host runs it before each input of a hosted conversation: an `input` to it (after the catch-up of the host agent), a `send` to a child, the first message of a spawned child, and each push of the host, such as the answers of a child, the answers of the user, and a delivery of an entry (see the input hooks in the [harness spec, Host](https://github.com/Vzlentin/harness/blob/f1cdbeb1496985c40c5fc24b598ffc865458f00c/docs/spec.md#host)). `head` is the ID of the newest head marker of the conversation (a `pi.compaction` or a `pi.reset`): a newer head marker means that its context lost the last digest. The entry has the request ID `input:digest:<count>:<hash>`, the count of digests of the caller and a hash of the text, and goes before the record, so a repeat after a crash adds nothing. A failure is the warning `digest: <message>` in `host.log` and the degraded state `digest-failed`, and the input goes through. The digest is not a part of the catch-up: a catch-up comes only before an input to the host agent, and its hooks do not know the agent.

## Memory

The host agent has a memory, an OptMem store. Its folder is the `.optmem` folder in the directory of the host when it exists, as `memoryDir(host, cwd)` of `@vzlentin/harness/hosts` gives it. Otherwise, and always for `main`, it is OptMem's default folder, `~/.optmem/memory`. The entry runs `~/.optmem/memo` with `MEMORY_DIR` set to that folder, or with no `MEMORY_DIR`. A missing `memo` gives the error `~/.optmem/memo is missing: install OptMem`. An error of `memo` is its error output, else its output.

The memory is only for the host agent. No child gets the `memory` tool or the memory section, at any depth (see `uninherited` in [Entry](#entry)).

### Memory section

The system prompt of the host agent has the section `memory` (`MEMORY_SECTION`): the line `# Memory, oldest first`, then each memory line of every part of `memo wake`, with no status line and no compression prompt. The entry takes this snapshot at the first model request of each conversation after the host starts, and keeps it until the host exits, so the section does not change during the life of the host. When `wake` prints `Cannot wake`, the entry first does the compressions, then runs `wake` one more time. An empty memory gives no section. A snapshot that fails, such as with no `memo`, gives no section and the warning `The memory section failed: <message>`.

### memory tool

The `memory` tool has one `action`. `note` saves `text`, trimmed, with `memo note`, and gives its line `Saved as #<N>.`, never the rest of the output. A note that `memo` refuses, such as a text over its limit of 280 bytes, fails with the error of `memo`. `recall` gives the output of `memo recall <pattern>`, and `zoom` the output of `memo zoom <block>`. A call goes to the host in its own process, as a `memory` request.

A `memory` request `{ action, ... }` uses the memory of the host agent. `note { text }`, `recall { pattern }` and `zoom { block }` are the calls of the `memory` tool: they run `memo` as the tool does, and reply `{ text }` with the result of the call. An error of the call fails the request with its message. `snapshot` replies `{ text }` with the text of the memory section, which the entry takes with `memo wake` at each request and does not keep, or with an empty `text` for an empty memory. A `snapshot` that gets `Cannot wake` first waits for the compressions. Each action has its own fields: a line without them fails with `Invalid memory request: <field>: required`. A `memory` request counts as activity for the idle exit.

### Compressions

The entry does the compressions of the memory in the background, so the agent never sees a compression prompt. A `note` whose output has a compression prompt (`Compress memories #<a>-<b> into one line of at most <N> bytes.`), and a `Cannot wake`, start a loop: `memo nap`, then for each prompt one model call and `memo nap <a>-<b> "<line>"`, until no prompt is left. The model gets the prompt without its `Run:` line and its count of the compressions left, with the thinking level `low`. The line is the first line of its answer that is not empty, trimmed, and cut to `<N>` bytes at the end of a word, else at the end of a character.

The model is the setting `memoryModel` of Pi's settings, read again at each compression, else `subagentModel`, else Pi's default model, as `settingModel` of `@vzlentin/harness/model-choice` finds it; its errors name `a compression`. One loop runs for each memory folder at a time: a note while it runs makes it run one more pass. A failure ends the loop with the warning `A compression of the memory failed: <message>`. While a loop runs, `busy` of the entry is true. A closing host stops the loop with no warning, and waits for its end.

## Watch

A `watch-project` request `{}` replies with the whole store, `{ persons, rules, threads, parleys, asks, items, degraded }`: each list of the store in ID order, in `asks` every ask, in `items` the open work items in ID order, each with its `stage` and `needsYou`, and in `degraded` the degraded states of the host, as the `degraded` handle lists them. Each thread has `waits` too: its messages in the state `draft` or `sent`, oldest first. The other messages of a thread come from `thread read`.

The entry reads the store again after each write of `project.sqlite` that changes a person, a rule, a thread, a message (a log, a mark, an edit or a delete), a parley or an item, after each commit that changes an ask, after each change of a child, its record, the started tasks or the labels of the tasks, after each task that ends, and after each change of the degraded states of the host, which is not a commit, and compares it with what the client has. It then sends one `{ "event": { persons, rules, threads, parleys, asks, items, removed, degraded } }` with the objects that are new or changed, in `removed` the IDs of each kind of the objects that went, and in `degraded` every degraded state. Every list is there, empty when nothing of its kind changed. A read that changes no object and no degraded state sends no event. The reads run one at a time, and the writes and the commits during a read give one more read and one more event. An event has an item when a write changes it or its edges, whatever its new state: an item that becomes `done` or `dropped` comes once with that state, and then no more. An event also has an open item when its `stage` or its `needsYou` changes: after a change of a parley, an ask, a child, the records of the children, the started tasks or the labels of the tasks, or after a task that ends, the read works out the stage of every open item again. No request retires an item, so `removed.items` is always empty. A slow client does not hold up the host: when a write must wait for the socket to drain, only that watch waits, and its next event has every object. A read that fails ends the connection, so the client opens a new watch. A request without a connection, such as one of `scope.send`, fails with `A watch-project watch needs a connection`. `ProjectState` and `ProjectEvent` of `src/protocol/project-watch.ts`, and `ProjectThread` of `src/protocol/project.ts`, are the TypeBox schemas of the reply, of an event and of a thread with its waits.

## Tools

The extension `harness-project` (`PROJECT_EXTENSION` of `src/protocol/project.ts`) of the entry has the tools `thread`, `rule`, `parley` and `item`, which read and change the store of the project. The host gives the tools of its entries to the host agent and to each child, also at the depth limit (see the [harness spec, Limits](https://github.com/Vzlentin/harness/blob/f1cdbeb1496985c40c5fc24b598ffc865458f00c/docs/spec.md#limits)). A client of `children.open` leaves them out, in the model tools and in `codemode`, when its `setup` adds `harness-project` to the `remove` of the `extensions` of the child's `AgentDoc`. Such a child still gets the section of the decided rules.

A call runs in the host process, and its caller is the conversation ID, which the entry keeps in `by` of each object that the call writes. The requests have no request ID, so a call that a host restart interrupts does not run again. It ends with `Tool <name> was interrupted and may have partially run`, so a message is never logged twice.

Each tool takes one `action` and its arguments, and sends the requests of that object:

| `thread` | `mark`   | `message`, `state`                                                                                              |

| `parley` | `round`  | `asks`, each with `ask` to replace an open ask, and `slug`, `title`, `goal`, `evidence`, `design_sense`, `item` |
| `parley` | `answer` | `answers`, each `{ ask, answer, label?, words? }`, and `slug`                                                   |
| `parley` | `drop`   | `ask`, `slug`                                                                                                   |
| `parley` | `note`   | `ask`, `note`, `slug`                                                                                           |
| `parley` | `take`   | `slug`                                                                                                          |

| `item`   | `add`    | `title`, `text`                                                                                                 |
| `item`   | `set`    | `id`, and `title`, `text`, `state`                                                                              |
| `item`   | `list`   | `state`                                                                                                         |
| `item`   | `read`   | `id`                                                                                                            |
| `item`   | `link`   | `from`, `kind`, `to`                                                                                            |

### thread and rule

- `log` adds a message `in` from the person `from`, with `at` when it is given. `draft` adds a message `out` from `user`, at the time of the write, so its state is `draft`. `mark` sends `message mark`. The `thread` tool sends no `thread add`, no `thread join`, no `message edit`, no `message delete` and no `state` of `message log`.
- `rule set` without `id` adds an open rule, and with `id` changes an open rule, as the `rule` request does. The `rule` tool has no `status`, and no action that decides, retires, edits as the user, creates or deletes a rule: an agent proposes a rule, and only the user puts it in effect. To change a decided rule, an agent adds a new rule that replaces it.
- Each `thread` and `rule` call also sends a `person list` request, for the names.

### parley

- Each `parley` call sends one request, except `list` and `answer`. `parley round` sends `ask round`, with the frame `{ slug, title, goal, evidence, design_sense }` of the fields that it gives as `parley` when it has `slug`, and `item` when it gives `item`. `parley answer` sends `ask answer` with no `user`, so its answers are the answers of the agent, `{ kind: "hosted", conversation }`, then a `todo list` request (see below). `parley drop` sends `ask drop`, `parley note` sends `ask note` with `note`, and `parley read` with `ask` sends `ask read`. The asks of `parley round` go as they are, with `ask` when an entry gives it. The description of `parley` and the parley skill tell the agent to fix an open ask with a round entry with `ask`. `parley take`, `parley end` and `parley read` with `slug` alone send the `parley` request of the action. `parley list` sends `parley list`, then `ask list`. With `slug`, `ask` is the number `n` of the ask in the parley, and the request names it as `{ slug, n }`. Without `slug`, `ask` is the ID of an ask, and the request names it as `{ id }`.
- The description of `parley` tells the agent how to write the answer line of the user, such as `[<slug>] 1a 3:"own words" 4b:"a note" ?5 ok`, with one `answer` call with `slug`: `<n><key>` is the answer `key` to the ask `n`, `:"<words>"` after it adds the words, `<n>:"<words>"` is `own` with a short label and the words, `?<n>` writes nothing, and `ok` is the plan of each open `my call` that the line does not name, and `ok` to the open read-back. The description of `parley` also gives the asker the vault flow of an ask: read the vault on the topic, write the view with `show-me` and wiki links to the notes that exist, and when the user answers and `VAULT` names a folder that exists, ask the next question first, then do the todo `Save to the vault: <title>`: write or update a note with an `id` in its front matter and record it with `note`, which closes the todo, or drop the todo with a one-line reason.

### item

- Each `item` call sends one `item` request of its action, with the caller for `add`, `set` and `link`. The tool has no `unlink`. The description of `item` tells the agent that talks with the user to add, reword, close, drop and link items from what the chat shows; a message to a person stays a thread draft, not an item.

### Refusals of the runners

The runner refuses a call without an argument that the action needs with `<action> requires <argument>`, before it sends a request: `read`, `log` and `draft` without `thread`, `log` without `from`, `log` and `draft` without `text`, `mark` without `message` or `state`, a `set` without `saidBy`, a new rule without `name`, `kind` or `value`, a `round` with neither `asks` nor `slug` (`round requires asks`), an `answer` without `answers`, a `drop` without `ask`, a `note` without `ask` or `note`, a `take` or an `end` without `slug`, an `end` without `status`, a `read` of `parley` with neither `slug` nor `ask` (`read requires ask`), an `item add` without `title`, an `item set` or an `item read` without `id`, and an `item link` without `from`, `kind` or `to`. A `round` with `title`, `goal`, `evidence`, `design_sense` or `item` and no `slug` fails with `round requires slug`. A `round` with `slug` and no `asks` sends `asks: []`. An `item link` with a `from` or a `to` that is not a reference fails with `Invalid item reference: <reference>`. The other errors come from the entry or the host.

### Text results

The text result has one line for each object.

- An author is `user`, or a person as `<name> (<id>)`, such as `Sam (1)`, or `person <id>` when the person has no name in the reply of `person list`. A thread is `<id> <topic> with <persons>: last message <time>`, or `no messages` in place of the time, with its persons as authors. A message is `<id> <time> <author> (<state>): <text>`. A rule is `<id> <name> (<kind>, <status>): <value> [said by <author> in message <source>; replaces <id>]`, without ` in message <source>` when it has no source, such as `[said by user]`, with `: "<words>"` after the author when it has words, such as `[said by user: "MDM est feminin"]`, and without `; replaces <id>` when it replaces none. A time is in ISO 8601, in UTC.
- `thread read` gives the line of the thread, then the line of each message, oldest first, or `No messages`. `thread list` gives the line of each thread, or `No threads`. `log`, `draft` and `mark` give the line of the message. `rule set` gives the line of the rule, and `rule list` the line of each rule, or `No rules`.
- The text of `parley` joins the fields of a line with `·`. A parley is `<slug> · <status> · <title>`. An ask is `<n> · <title> · <kind> · open · plan <key> · <label>` while it is open, `<n> · <title> · <kind> · <answer> · <label>` when it is answered, and `<n> · <title> · <kind> · dropped` when it is dropped. `<n>` is its number in its parley, or its ID when it has no parley. A field that the ask does not have is left out: `<kind>`, and `plan <key> · <label>` with no plan. The label of an open ask is the label of the option of its plan. The label of an answer is the `own` label, the label of the option of the key, or the label of the answer for `ok`.
- The text of a parley is its line, the line of each of its asks in the order of their numbers, each open ask followed by the line of each of its options, and each answered ask followed by each of the words of the user on its own line, then one last line. An option line is two spaces, then `<key> · <label>`, then `gains: <gain>; <gain>` and `costs: <cost>; <cost>` when the option has them. For an open parley, the last line is the answer line: `[<slug>]`, then `<n><plan>` for each open `your call` with a plan, then `ok` when no ask is open or when another ask is open. For any other status, the last line is `harness parley show <slug>`.
- `round`, `answer` and `drop` give the text of each parley of the reply, then the line of each ask with no parley of the reply. `answer` then gives the line of each open todo of the caller's list that belongs to an ask of the reply, such as the todo `Save to the vault` that the answer added: it sends a `todo list` request for that. `take` and `read` with `slug` give the text of the parley, `end` gives the line of the parley, `note` gives the line of the ask, and `read` with `ask` gives the line of the ask, then its `view`. `list` gives the line of each parley, or `No parleys`, then the line of each open ask with no parley.
- The text of an item is its line `<mark> <id> <stage> <title>`, where the mark is `?` when the item needs you, else `○` for open, `✓` for done and `✗` for dropped. `add` and `set` give the line of the item, `list` the line of each item or `No items`, `read` the line, the text of the item when it is not empty, and one line `<from> <kind> <to>` for each edge, and `link` the line of the edge. The text of `read` has the `needs` edges that go to the item after its own edges, as the reply of `item read` has them. `itemLine`, `itemText` and `edgeLine` of `src/protocol/item.ts` give these texts.

### Structured results

The structured result is `{ action, value }`, where `value` is the reply of the request: the message for `log`, `draft` and `mark`, the rule for `rule set`, `{ thread, messages }` for `thread read`, and `{ threads }` or `{ rules }` for `list`. For `parley`, `value` is the write `{ parleys, asks }` for `round`, `answer` and `drop`, the ask for `note` and for `read` with `ask`, `{ parley, asks }` for `take` and `read`, the parley for `end`, and `{ parleys, asks }` with the open asks with no parley for `list`. For `item`, `value` is the item with its stage for `add`, `set` and `read`, `{ items }` for `list`, and the edge for `link`. Each tool declares the schema of this result, with the schemas `ThreadList`, `ThreadMessages`, `Message`, `RuleList`, `Rule` and `ParleyList` of `src/protocol/project.ts`, `Ask`, `Parley`, `ParleyAsks`, `AskList` and `AskWrite` of `@vzlentin/harness/protocol`, and `StagedItem`, `ItemList` and `Edge` of `src/protocol/item.ts`.

## CLI

The package has the command `projects` (`bin` of `package.json`, `src/cli.ts`, `dist/cli.js` in a build). It has these commands:

```
projects parley show <slug> [--json]
projects parley note [<slug>] <ask> <note>
projects rule [list [--kind <kind>] [--status <status>]]
projects rule (decide | retire | delete) <id>
projects rule edit <id> [--name <name>] [--kind <kind>] [--value <text>]
projects rule create --name <name> --kind <kind> --value <text>
projects item [list [--state <state>]]
projects item add <title> [--text <text>]
projects item set <id> [<state>] [--title <title>] [--text <text>]
projects item show <id>
projects item link <from> <kind> <to>
projects store load <file>
```

Each command prints its result on stdout. An error prints one line on stderr, and the exit code is 1. Any other word, a missing argument, or an option that the action does not take prints the usage on stderr, with the exit code 1: `Usage:`, the lines above, each after two spaces, and `Any command takes --host <name> before it; without it, the host is HARNESS_HOST, then the cwd.`

### Host of a command

The host of a command is `--host <name>` when it is the first argument, else `HARNESS_HOST`, else the registered host whose directory holds the cwd, else `main`, as for the `harness` CLI. A `--host` after the command is an argument of that command. An unknown host fails with `Unknown harness host: <name>`. A first argument `--project` fails with `projects takes --host <name>, not --project`.

A command other than `store load` sends its requests through the socket of the host, and starts the host when none runs: a request of a core type of the host, such as `person list` or `todo list`, as a request of the host, and a request of the projects entry as a request of an entry. The caller is `PI_SESSION_ID`, else `cli`. A host that does not load the projects entry answers with `no loaded entry serves request type "<type>"`.

### parley, rule and item

- `parley show <slug>` sends `parley read` and prints the parley as Markdown: its title, with ` (<status>)` when it is done or dropped, its goal, each ask with its answer and the words of the user, or `Open, plan <key>: <label>` for an open ask, without the read-back, then its design sense and its evidence. With `--json`, it prints the reply as one JSON line. `parleyShowText` of `src/protocol/project.ts` gives the Markdown. An unknown slug fails with `Unknown parley: <slug>`.
- `parley note` sends `ask note` with the note, and prints the line of the ask. With `<slug>`, `<ask>` is the number of the ask in the parley, else its ID. An `<ask>` that is not a positive integer fails with `Invalid ask: <ask>`.
- `rule` lists the rules, as `rule list` of the tool, with the filter of `--kind` and `--status`. The other actions send the `rule` request of the action as the user, and print the line of the rule (see [Text results](#text-results)). The action is only the first argument after `rule`, so an option before it gives the usage. An `<id>` that is not a positive integer fails with `Invalid rule id: <id>`, and a kind or a status that is not one fails with `Invalid rule kind: <kind>` or `Invalid rule status: <status>`.
- `item` runs the `item` tool with the action `list`, `add`, `set`, `read` (`show`) or `link`, and prints its text result (see [item](#item)). The words of `add` after the action are the title. An `<id>` that is not a positive integer fails with `Invalid item id: <id>`, a state that is not one fails with `Invalid item state: <state>`, and a kind that is not one with `Invalid edge kind: <kind>`.
- An option that the command does not know, or that comes twice, fails with `Unknown <command> argument: <option>`, and an option without its value fails with `<option> requires a value`.

### store load

`store load <file>` writes the store file `<file>` (see [Store file](#store-file)) into the empty `project.sqlite` of the host while no host runs, and prints `<list>: <count>` for each list of the file that `project.sqlite` keeps: `persons`, `threads`, `messages`, `rules`, `parleys`, `outbox` and `items`. It checks the file before it opens a store, with the errors of [Store file](#store-file). The asks, the todos and the todos of the callers belong to the harness host, and `store load` does not load them: a file with an ask, a todo of `todos` other than a todo that the move of the todos made `dropped`, or a todo in `callerTodos` fails with `<file> has asks or todos: they belong to the harness host, and projects store load does not load them`, before any write. It takes the lock of the host, else it fails with `A harness host runs for <host>: stop it, then run projects store load again`. When a list of `project.sqlite` is not empty, it fails with `The store of <host> is not empty: projects store load writes only into an empty store`, and writes nothing.

It writes the persons, the threads with their messages, the rules, the parleys and the items with their edges of the file into `project.sqlite`, with their IDs, in one transaction. It does not open `durable.sqlite`. The `thread` of a rule with a `source` is the thread of its source message, whatever `thread` the file gives, and a rule with no `source` has no `thread`. Each message out keeps its `state` and the last change of its state from `changed`. The highest ID that a rule had is the higher of `lastRule` and the highest ID of `rules`, so the ID of a deleted rule is never given again. The `last` of the counter of the IDs of items is the higher of `lastItem` and the highest ID of `items`, and `store load` always writes the counter, so the move of the todos at the next start does nothing. When there is no `project.sqlite`, it writes `project.sqlite.import`, and renames it to `project.sqlite` only after its commit: a failure leaves no `project.sqlite` and no `project.sqlite.import`. An empty `project.sqlite` keeps its ID counters.

## Pi package

The Pi package is the npm package `@vzlentin/pi-projects`, from the `pi/` folder of this repository. It has the same version as `@vzlentin/projects`, and depends on `@vzlentin/projects` at that exact version. It has no copy of the projects package or of harness. The `pi` field of its `package.json` lists the extension, `./index.ts`, and the `skills/` folder, with the `parley` skill, `pi/skills/parley/SKILL.md`. The `piDurable` field lists `./entry.js`, so a host of the harness of the same Pi install loads the projects entry (see [Entry](#entry)).

The extension gives a Pi session the `thread`, `rule`, `parley` and `item` tools, the digest and the section of the decided rules before each turn, the `memory` tool and the memory section, `/rules`, and `/drafts`. It registers them in this order. It resolves `@vzlentin/projects` from its own folder, and loads the `dist/` modules `project-tool`, `memory-tool`, `protocol/project` and `protocol/requests` through the `exports` of that package. It loads `@vzlentin/harness/client`, `/tool` and `/protocol` from the folder of `@vzlentin/projects`, so it uses the harness of the projects package, not another copy, such as an older one of pi-agents that npm can hoist. The files of `pi/` import `../src`, `../dist` and `@vzlentin/harness` only for types; `no-restricted-imports` in `vite.config.ts` refuses a runtime import of them. When Pi loads the extension, it also puts the `.bin` folder of the `node_modules` folder that holds `@vzlentin/projects` last on the `PATH` of Pi's process, so the agents find `projects`. It goes last because the folder also holds the commands of other dependencies, such as an older `pi`, which must not hide the user's own. It first removes that folder from `PATH`, so each load leaves it there once. When one of the modules does not load, such as in a checkout without `npm run build`, Pi shows that the extension failed to load.

The extension sends its requests with `requestEntry` of `@vzlentin/harness/client` or with `sendToHost` of `@vzlentin/harness/tool`, and checks each reply against its schema with `replyOf`. A reply of another shape fails with `The host replied with no <value>`.

The `thread`, `rule`, `parley` and `item` tools have the parameters, the descriptions, the text results and the structured results of the tools of the host (see [Tools](#tools)), and run the same runners: `projectTools({ Type }, adapt)` gives each tool to `adapt`, which registers it. The calls go to the host with `sendToHost`, so they start the host when none runs. The caller is the session ID. A round with one of these calls runs all of its tool calls in order, because each call has its own connection.

Before each turn of the session (`before_agent_start`), the extension sends a `digest` request with the session ID as the caller, and starts the host when none runs. The request has as `head` the ID of the newest entry of the type `compaction` on the branch of the session, when it has one. When the reply has a text, the turn gets it as a custom message of the type `harness-digest`, which Pi gives the model and does not show. A request that fails gives no message, and a notification `harness: no digest: <error>` with a UI.

Before each turn, the extension also sends `rule list` with the status `decided`, only when a host runs. When `rulesSection` gives a text for the reply, the turn has it as the system prompt section `project_rules` (see [Rules section](#rules-section)). With no host, no decided rule, or a request that fails, the turn has no such section; a request that fails also shows the notification `harness: no rules: <error>` with a UI.

The `memory` tool has the name, label, description and parameters of the `memory` tool of the host agent (see [memory tool](#memory-tool)), from `memoryTool({ Type }, adapt)`. Its calls go to the host with `sendToHost`, so a call starts the host when none runs, and the result is the `text` of the reply. The session uses the memory of the host agent of that host: the `MEMORY_DIR` of Pi's process has no effect. At the first turn of a session, the extension sends a `memory` request with the action `snapshot`, with a start. It keeps the reply for the session ID, and each turn of the session gets its text as the system prompt section `memory`, after the section of the decided rules. A reply with an empty text gives no section. A snapshot that fails gives the session no section and no new request, and the notification `harness: no memory: <error>` with a UI.

`/rules` lists the rules of the project, the open ones first, then the decided ones, then the retired ones, each as its line. It sends its requests with `sendToHost`, and the caller is the session ID. With a UI, a select shows `New rule` and the line of each rule. For a rule, a second select gives the actions of its status: `Decide`, `Retire`, `Edit` and `Delete` for an open rule, `Retire`, `Edit` and `Delete` for a decided rule, and `Edit` and `Delete` for a retired rule. `Edit` asks the name, with the current name as the placeholder, then the value in the editor; an empty answer keeps the field. `Delete` asks a confirm first. `New rule` asks the name, the kind and the value. The command sends the `rule` request of the action, and notifies the line of the rule of the reply. A cancel at any step sends nothing. With no UI, it writes the lines to stdout and changes nothing. An error is the notification `harness: <error>`, or that line on stderr with no UI.

`/drafts` copies a draft of a thread to the clipboard, only in Pi's interactive mode; in another mode, it shows the error `/drafts requires interactive mode`. It reads the threads of the project with `thread list` and `thread read`, through `sendToHost`, so it starts the host when none runs, and keeps the messages out in the state `draft`. A read that fails shows the warning `Could not read the drafts: <error>`, and copies nothing. With no draft, it shows `No drafts to copy`. Else a select shows each draft as `Draft <id>: <first line that is not empty, at most 60 characters>`. It puts the text of the picked draft on the clipboard with Pi's `copyToClipboard`, and shows `Copied <n> lines: <first line>`. A copy that fails shows the error `Copy failed: <error>`, and marks nothing. After the copy, for each draft that it read whose text the copied text holds, with each run of whitespace as one space and without whitespace at the ends, it sends `message mark` with the state `sent`, with the session ID as the caller, and shows `Draft <id> marked sent`. A mark that fails shows the warning `Could not mark draft <id> sent: <error>`, and the next draft goes on.
